# 科研 Pipeline 设计草案

日期：2026-11-11。状态：供讨论的设计，尚未实现统一 Pipeline 执行器。

用户希望把相近的 Skills 与 MCP 组合成面向结果的 Pipeline，已明确的两个入口是“单篇论文总结”和“专题调研”。本文建议先规划 8 种工作流，优先实现这两种，再按实际使用增补。其他六种尚不是用户确认的开发范围。

## 设计方式

顶层按用户输入和最终交付物划分。一个 Pipeline 可以组合多个 Skill、调用多个 MCP，也能调用另一个 Pipeline。抓取、分段阅读、分类、引用导出、校验和发布作为共享步骤，避免重复实现。

沿用 `research-orchestrator` 作为统一入口，支持“输入论文链接”或“输入研究问题”自动选择工作流；保留单独调用特定工作流的方式。现有八个 Skills 和二十八个 MCP 工具可以作为实现材料。统一执行器、运行记录、步骤衔接和恢复机制仍需新增。

Skill 负责问题理解、阅读、模型总结和研究判断；MCP 负责确定性的获取、状态、引用校验与保存。默认使用当前代理完成推理。需要后台无人值守执行时，另用显式配置的模型 API；一个同步 MCP 调用不能凭空使用外层客户端的模型。

## 建议的 8 条 Pipeline

1. **单篇精读与入库 `paper-summary`**
   - 输入：论文链接、arXiv ID 或支持的论文网页，可选阅读重点。
   - 输出：中文结构化笔记、具身要素、证据定位、标签和文献引用。
   - 路径：身份与版本确认 → 本库检查 → 获取原文 → 阅读方法/实验/局限 → 带证据总结 → 分类与校验 → 保存。
   - 复用：`paper-ingest`、局部证据检索、引用导出、库校验。

2. **专题调研 `topic-research`**
   - 输入：研究问题、研究范围，可选候选数/精读数/检索轮数上限。
   - 输出：有检索与筛选记录的综述、方法分类、比较矩阵、共识/分歧/研究缺口和参考文献。
   - 路径：明确问题 → 复用本库 → 多源检索 → 去重与筛选 → 对选定论文调用 `paper-summary` → 跨论文综合 → 校验与保存。
   - 复用：`paper-discover`、队列、单篇 Pipeline、`paper-research`、`paper-compare`、引用导出。
   - 范围约束：报告实际检索与精读范围，达到预算时说明未覆盖部分。

3. **多篇论文比较与选型 `paper-comparison`**
   - 输入：指定论文/方法与比较目标，如跨本体迁移或实机部署约束。
   - 输出：条件对齐矩阵、方法差异、适用场景、证据不足项和有条件的选型建议。
   - 重点：分别检查任务、本体、数据、成功率分母与 seen/unseen 条件，再讨论数值。
   - 可独立使用，也作为专题调研的综合步骤。

4. **复现准备与实验计划 `reproduction-plan`**
   - 输入：一篇论文和目标，如复现某张表、运行推理或移植到另一机器人。
   - 输出：已报告配置、代码/数据/权重线索、缺失条件、分阶段验证计划与验收标准。
   - 复用：单篇 Pipeline、`paper-reproduce`、可用的只读仓库工具和研究报告 `planning`。
   - 计划与实际执行分别记录；复现执行和结果对账可在取得真实实验数据后扩展。

5. **相关工作拓展与阅读路线 `related-work`**
   - 输入：一篇或少量种子论文，以及想补充的知识方向。
   - 输出：前置工作、同期方法、后续工作组成的有理由阅读清单，以及建议阅读顺序。
   - 路径：种子身份确认 → 有界参考文献/被引关系 → 补充检索 → 摘要筛选 → 保存候选队列。
   - 适合“读完这篇接着读什么”；默认交付阅读路线，不要求把所有候选精读入库。

6. **研究问题与实验方案 `research-proposal`**
   - 输入：研究方向、现有调研结果，以及可用机器人/数据/算力等约束。
   - 输出：候选假设、文献依据、与既有工作的关系、最小验证实验、消融和判定标准。
   - 复用：专题调研、比较与复现准备；建议和假设进入 `planning`。
   - 新颖性按检索范围表述，需要后续验证，不能把未发现相关工作写成确定不存在。

7. **实验结果分析与下一轮迭代 `experiment-analysis`**
   - 输入：实验配置、日志、指标，按需补充机器人轨迹或视频，以及对应论文/计划。
   - 输出：可追溯的结果图表、与目标/基线的差距、失败案例分类和下一轮实验建议。
   - 重点：关联代码与配置版本、任务与随机种子、试验分母及失败条件，区分测量、解释和建议。
   - 该条需要新增实验产物的导入与证据合同，当前论文 evidence ID 不能直接充当日志/视频证据；适合后期扩展。

8. **论文库整理与质量维护 `library-curation`**
   - 输入：整个本库，或指定标签/专题范围。
   - 输出：重复/多版本候选、分类不一致、阅读范围不足、引用问题和过期报告清单，以及范围明确的修复结果。
   - 复用：`library-maintain`、本地检索、校验、批注修订检查。
   - 自动处理可确定的修复；身份合并、人工批注修改和不确定分类需要对应任务授权及实际判断。
   - 论文新版本检查可作为此 Pipeline 的一种模式：比对新旧证据，更新生成区并标出受影响报告；版本差异分析与报告依赖更新还需开发。持续监测是可选触发方式，另需用户明确安排。

## 第一期交付范围建议

先把 `paper-summary` 与 `topic-research` 做成可安装、可恢复的完整入口。比较、引用导出与校验先作为可复用步骤提供，避免同时维护八套尚未验证的执行逻辑。

每次运行至少记录：`run_id`、Pipeline 类型、输入与范围、预算、步骤状态、论文版本、证据包/输出路径、失败原因及下一步。中断后复用已经成功的抓取和笔记，恢复时检查来源及目标文件修订。

模型步骤要有明确的“等待代理结果”状态。代理提交符合 schema 的结果后，MCP 校验并推进下一步；不把提示词指令当成已经执行的处理步骤。外部服务限流、全文不可得或版本不明时，标记等待/失败或明确的摘要范围，不静默跳过后宣布全流程成功。

运行状态和原文证据默认保留本地缓存，最终 Markdown/引用/筛选记录随 Git 同步。在另一台电脑上需重新获取缓存时，以稳定论文身份、版本和证据校验值重建，不能直接信任旧电脑的缓存路径。

发布作为各条内容 Pipeline 可配置的末端步骤，遵循当前任务与仓库已有授权；引用导出、标签分类同样作为共享步骤。它们也保留独立工具，供用户只执行某个小操作。

## 后续实施顺序建议

1. 单篇总结、专题调研，以及共用的运行状态/恢复接口。
2. 多篇比较、复现准备、相关工作路线，复用第一期执行器。
3. 在实际使用中验证研究方案、实验结果分析和整库维护的输入输出，再决定自动化程度。

当前草案不创建定时任务，不新增外部 MCP 连接，不改变现有网站发布设置。
